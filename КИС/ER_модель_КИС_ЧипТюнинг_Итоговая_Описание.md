## 1. Исправление критических и логических ошибок

В новой итоговой модели устранены все замечания:

1. **Устранение избыточности связей и дублирования FK (Строгая 3NF):**
   - **Удален `vin_code` из `Work_Order`:** автомобиль однозначно определяется через заявку-основание `Work_Order.id_request -> Service_Request.vin_code`. Связь `1 : N [Обслуживается]` между `Vehicle` и `Work_Order` удалена, замкнутый циклический контур ликвидирован.
   - **Удален избыточный `id_client` из `Service_Request`:** заявка оформляется на конкретный автомобиль `Service_Request.vin_code [FK]`, а владелец автомобиля уже строго зафиксирован в `Vehicle.id_client [FK]`. Цепочка связей стала строго иерархической: `Client (1) -> (N) Vehicle (1) -> (N) Service_Request`.
   - **Ликвидирована двойная связь у `Work_Completion_Act` (Акт):** удалена избыточная связь от `Order_Execution` к `Work_Completion_Act`. Оставлена единственная прямая сплошная связь `Work_Order (1) -> (0..1) Work_Completion_Act`, строго опирающаяся на внешний ключ `id_order` в таблице Акта.

2. **Обеспечение атомарности атрибутов (1NF и 3NF):**
   - Поле `brand_model` в таблице `Vehicle` разделено на два атомарных поля: `brand : VARCHAR(50)` и `model : VARCHAR(50)`.
   - Поле `engine_and_ecu` в таблице `Vehicle` разделено на два атомарных поля: `engine_model : VARCHAR(50)` и `ecu_type : VARCHAR(50)`.
   - Поле `dtc_errors` в таблице `Diagnostic_Card` заменено на атомарный код ошибки `dtc_fault_code : VARCHAR(10)` (например, `P0171`, либо `'NONE'`), исключая ненормализованные списки через запятую.

3. **Коррекция кардинальности и обязательности связей (1 : 0..1):**
   - В нотации Crow's Foot связи в производственном контуре (`Service_Request -> Work_Order`, `Work_Order -> Order_Execution`, `Work_Order -> Work_Completion_Act`) обозначены как **необязательные со стороны дочерних документов** `1 : 0..1` (графический символ `0|` — кружок и вертикальная черта):
     - Заявка может существовать без наряд-заказа (клиент отказался от работ после консультации);
     - Наряд-заказ может быть открыт, но еще не передан в исполнение калибровщику;
     - Исполнение может быть завершено, но акт еще не подписан клиентом.
   - На уровне таблиц для обеспечения однозначности отношений `1 : 0..1` внешние ключи снабжены модификатором уникальности: `[FK] id_request : INT [UQ]`, `[FK] id_order : INT [UQ]`.

4. **Чистка технических обозначений и нотации:**
   - Убрано дублирование `(FK)` в конце строк — оставлен только четкий префикс `[FK]` в начале строки.
   - В подписи схемы зафиксирована строгая формулировка: **«нотация Crow's Foot / Воронья лапка»** (исключено упоминание IDEF1X, использующего кружки).

5. **Решение проблемы с открытием файла Visio:**
   - Документ сохранен в стандартном формате **`.vsd`** ([ER_модель_КИС_ЧипТюнинг_Итоговая.vsd](file:///c:/Users/danch/OneDrive/Рабочий%20стол/stage5/КИС/ER_модель_КИС_ЧипТюнинг_Итоговая.vsd)), который открывается во всех версиях Microsoft Visio (2010, 2013, 2016, 2019, Office 365) без ошибок несовместимости форматов.

## 3. Спецификация нормализованных сущностей (8 таблиц, 3NF)

### 1. `Client` (Клиенты автосервиса)
| Поле | Тип данных | Ключ | Назначение |
| :--- | :--- | :---: | :--- |
| `id_client` | INT | **[PK]** | Уникальный код клиента |
| `full_name` | VARCHAR(100) | | ФИО владельца / наименование юрлица |
| `phone_number` | VARCHAR(20) | | Контактный номер телефона |
| `client_type` | VARCHAR(20) | | Тип клиента («Физлицо», «Юрлицо») |

### 2. `Vehicle` (Обслуживаемые автомобили)
| Поле | Тип данных | Ключ | Назначение |
| :--- | :--- | :---: | :--- |
| `vin_code` | VARCHAR(17) | **[PK]** | 17-значный VIN-код транспортного средства |
| `id_client` | INT | **[FK]** | Владелец авто (`Client.id_client`) |
| `brand` | VARCHAR(50) | | Марка автомобиля (например, «BMW») |
| `model` | VARCHAR(50) | | Модель автомобиля (например, «530d») |
| `engine_model` | VARCHAR(50) | | Модификация ДВС (например, «3.0 B57D30») |
| `ecu_type` | VARCHAR(50) | | Модель блока ЭБУ (например, «Bosch MD1CS001») |
| `production_year` | INT | | Год выпуска |

### 3. `Diagnostic_Card` (Диагностическая карта ДВС)
| Поле | Тип данных | Ключ | Назначение |
| :--- | :--- | :---: | :--- |
| `id_diag` | INT | **[PK]** | Уникальный номер диагностической карты |
| `id_order` | INT | **[FK]** | Наряд-заказ (`Work_Order.id_order`) |
| `id_diagnostician` | INT | **[FK]** | Специалист-диагност (`Employee.id_employee`) |
| `diag_stage` | VARCHAR(20) | | Этап («Входная», «Выходная») |
| `dtc_fault_code` | VARCHAR(10) | | Атомарный код ошибки OBD-II (или «NONE») |
| `diag_conclusion` | VARCHAR(50) | | Заключение («Допущен к прошивке», «Исправен») |

### 4. `Employee` (Штатный персонал автосервиса)
| Поле | Тип данных | Ключ | Назначение |
| :--- | :--- | :---: | :--- |
| `id_employee` | INT | **[PK]** | Табельный номер сотрудника |
| `full_name` | VARCHAR(100) | | ФИО сотрудника |
| `role_title` | VARCHAR(50) | | Должность («Мастер-приемщик», «Диагност», «Тюнер») |
| `phone_number` | VARCHAR(20) | | Рабочий телефон |

### 5. `Service_Request` (Заявки клиентов — этап Данила)
| Поле | Тип данных | Ключ | Назначение |
| :--- | :--- | :---: | :--- |
| `id_request` | INT | **[PK]** | Номер заявки клиента |
| `vin_code` | VARCHAR(17) | **[FK]** | Автомобиль (`Vehicle.vin_code`) |
| `request_date` | DATETIME | | Дата и время поступления заявки |
| `tuning_goals` | VARCHAR(200) | | Цели чип-тюнинга («Stage 1», «Евро-2», «Откл. EGR») |
| `request_status`| VARCHAR(30) | | Статус заявки («Новая», «Согласована», «Отказ») |

### 6. `Work_Order` (Наряд-заказ — ключевой документ Данила)
| Поле | Тип данных | Ключ | Назначение |
| :--- | :--- | :---: | :--- |
| `id_order` | INT | **[PK]** | Номер наряд-заказа |
| `id_request` | INT | **[FK] [UQ]** | Заявка-основание (уникальный ключ 1:0..1) |
| `id_master` | INT | **[FK]** | Ответственный мастер-приемщик (`Employee`) |
| `order_number` | VARCHAR(30) | | Печатный номер («НЗ-2026/04-118») |
| `order_date` | DATETIME | | Дата и время открытия наряда |
| `order_status` | VARCHAR(30) | | Статус («В работе», «Выполнен», «Закрыт») |
| `total_agreed_cost` | DECIMAL(10,2) | | Согласованная стоимость работ (руб.) |

### 7. `Order_Execution` (Исполнение калибровки — этап Карима)
| Поле | Тип данных | Ключ | Назначение |
| :--- | :--- | :---: | :--- |
| `id_execution` | INT | **[PK]** | Идентификатор записи процесса прошивки |
| `id_order` | INT | **[FK] [UQ]** | Наряд-заказ (уникальный ключ 1:0..1) |
| `id_tuner` | INT | **[FK]** | Инженер-калибровщик (`Employee`) |
| `firmware_version` | VARCHAR(50) | | Версия калибровки («Stage1_DynoTune_v3») |
| `power_increase_hp` | INT | | Расчетный прирост мощности (л.с.) |
| `technical_comment` | TEXT | | **Обязательный комментарий мастера по заданию** |
| `execution_status` | VARCHAR(30) | | Статус («Завершена успешно») |

### 8. `Work_Completion_Act` (Акт выполненных работ — ключевой документ Карима)
| Поле | Тип данных | Ключ | Назначение |
| :--- | :--- | :---: | :--- |
| `id_act` | INT | **[PK]** | Идентификатор акта выполненных работ |
| `id_order` | INT | **[FK] [UQ]** | Наряд-заказ (уникальный ключ 1:0..1) |
| `id_master` | INT | **[FK]** | Мастер, подписавший акт (`Employee`) |
| `act_number` | VARCHAR(30) | | Номер акта («АКТ-2026/04-118») |
| `act_date` | DATETIME | | Дата закрытия и выдачи авто |
| `total_paid_amount` | DECIMAL(10,2) | | Оплаченная сумма (руб.) |
| `warranty_months` | INT | | Срок гарантии (мес.) |
| `is_signed` | BOOLEAN | | Признак подписания обеими сторонами |

## 4. Спецификация межтабличных связей (Реляционная целостность)

| № | Связь (Родитель $\rightarrow$ Дочерняя) | Кардинальность | Внешний ключ | Обоснование / Бизнес-смысл |
| :-: | :--- | :---: | :--- | :--- |
| 1 | `Client` $\rightarrow$ `Vehicle` | 1 : N (`\|\|` — `\|<`) | `Vehicle.id_client` | Один клиент может владеть парком из нескольких автомобилей |
| 2 | `Vehicle` $\rightarrow$ `Service_Request` | 1 : N (`\|\|` — `\|<`) | `Service_Request.vin_code` | На один автомобиль подаются заявки на чип-тюнинг |
| 3 | `Service_Request` $\rightarrow$ `Work_Order` | 1 : 0..1 (`\|\|` — `0\|`) | `Work_Order.id_request` | Утвержденная заявка порождает наряд-заказ (необязательная связь) |
| 4 | `Work_Order` $\rightarrow$ `Diagnostic_Card` | 1 : N (`\|\|` — `\|<`) | `Diagnostic_Card.id_order` | В рамках наряда проводятся входная и выходная диагностики |
| 5 | `Work_Order` $\rightarrow$ `Order_Execution` | 1 : 0..1 (`\|\|` — `0\|`) | `Order_Execution.id_order` | Наряд передается на калибровку инженеру-тюнеру |
| 6 | `Work_Order` $\rightarrow$ `Work_Completion_Act`| 1 : 0..1 (`\|\|` — `0\|`) | `Work_Completion_Act.id_order`| Выполненный наряд закрывается подписанием финансового акта |
| 7 | `Employee` $\rightarrow$ `Diagnostic_Card` | 1 : N (`\|\|` — `\|<`) | `Diagnostic_Card.id_diagnostician`| Диагност проводит тесты ДВС |
| 8 | `Employee` $\rightarrow$ `Work_Order` | 1 : N (`\|\|` — `\|<`) | `Work_Order.id_master` | Мастер-приемщик курирует наряд-заказ |
| 9 | `Employee` $\rightarrow$ `Order_Execution` | 1 : N (`\|\|` — `\|<`) | `Order_Execution.id_tuner` | Инженер-калибровщик выполняет запись калибровок и пишет комментарий |
| 10 | `Employee` $\rightarrow$ `Work_Completion_Act`| 1 : N (`\|\|` — `\|<`) | `Work_Completion_Act.id_master` | Мастер оформляет и подписывает акт выполненных работ |
